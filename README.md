# ESoil Proceedings

Воспроизводимый конвейер подготовки сборника тезисов конференции из Pretalx
API: загрузка, нормализация, редакторская проверка и генерация PDF через
Jinja2 и LuaLaTeX.

## Установка

Требуются:

- Python 3.11+ и [uv](https://docs.astral.sh/uv/);
- TeX Live или MiKTeX с командами `lualatex` и `latexmk`;
- Poppler с `pdftoppm` — только для `render-preview`.

Установка Python-зависимостей:

```bash
uv sync
```

Создайте локальный файл настроек из шаблона:

```bash
cp .env.template .env
```

В PowerShell:

```powershell
Copy-Item .env.template .env
```

Затем отредактируйте `.env`:

```dotenv
PRETALX_API_TOKEN=...
PRETALX_BASE_URL=https://conf.esoil.ru
PRETALX_EVENT=pgb2026
```

При переходе на следующую конференцию достаточно изменить `PRETALX_EVENT`.
Файл `.env` читается автоматически, игнорируется Git и не должен передаваться
другим людям. `.env.template` хранится в репозитории без токена. Уже заданные
системные переменные окружения имеют приоритет над `.env`.

Токен можно оставить пустым, если достаточно публичного API. Не передавайте
его аргументом CLI: он может попасть в историю shell. Токен не записывается в
выходные файлы и не выводится в сообщения программы.

Фильтры `proceedings.include_states` и `proceedings.include_submission_types`
находятся в `config/conference.yaml`. По умолчанию включаются только
подтверждённые постерные, гласные и пленарные доклады; слушатели и прочие
программные элементы в сборник не попадают.

## Использование

```bash
uv run esoil-proceedings fetch
uv run esoil-proceedings normalize
uv run esoil-proceedings validate
uv run esoil-proceedings build
uv run esoil-proceedings all
```

`build` и `render-preview` перед запуском обновляют отчёт валидации и
останавливаются только на `ERROR` (например, ссылка на несуществующую аффилиацию).
`WARNING`, включая отсутствие тезисов, и `INFO` сборку не блокируют.
Для осознанной сборки с незакрытыми структурными ошибками используйте `--force`:

```bash
uv run esoil-proceedings build --force
```

Можно указать другой конфиг перед именем команды:

```bash
uv run esoil-proceedings --config config/conference.yaml all
```

Команды создают:

- `data/raw/submissions.json` — все полученные страницы API, объединённые в
  один список без изменения полей заявок;
- `data/raw/speakers.json` — отдельная выгрузка докладчиков, необходимая для
  получения email по speaker code;
- `data/proceedings.yaml` — нормализованные данные схемы 2 для редакторской
  проверки и генерации LaTeX;
- `build/qa-report.json` и `build/qa-report.txt` — единый QA-отчёт с уровнями
  `INFO`, `WARNING`, `ERROR`, кодами диагностик и проблемными значениями;
- `build/validation.csv` — ошибки и предупреждения по каждой заявке (UTF-8 с
  BOM, поэтому файл корректно открывается в Excel);
- `build/validation.md` — человекочитаемый отчёт: после краткой сводки
  проблемные заявки сгруппированы по секциям, а диагностические сообщения
  приведены на русском языке;
- `build/proceedings.tex` — воспроизводимый LaTeX-источник;
- `build/proceedings.pdf` — итоговый сборник;
- `build/build.log` — полный журнал LuaLaTeX/latexmk;
- `build/render_warnings.csv` — совместимый CSV-экспорт той же валидации;
  renderer больше не ищет и не исправляет ошибки данных;
- `build/page-labels.json` — карта меток и страниц для проверки PDF.

`all` последовательно выполняет `fetch`, `normalize`, `validate`. Клиент
использует таймаут 30 секунд и до четырёх попыток для 429, 5xx и сетевых
ошибок. Ответы 401/403 завершают команду с понятным сообщением.

Метаданные обложки и выходной страницы, УДК/ББК, библиографическое описание и
репозиторные пути к изображениям настраиваются в `config/conference.yaml`.
Там же задаются логотипы официальных спонсоров и партнёра. Пленарные доклады
выводятся первым самостоятельным блоком, затем PDF группируется по секциям;
порядок заявок внутри каждого блока сохраняется из `data/proceedings.yaml`.

Для визуальной QA-проверки обложки, выходных данных, оглавления, примеров
докладов и всех страниц секции «Биота» выполните:

```bash
uv run esoil-proceedings render-preview
```

PNG будут сохранены в `build/preview/`.

## Правила данных

Поле `description` разбирается по запятым и `;` как ключевые слова. Ответ на вопрос
`CDHXWQFZ` разбирается по `;`, а имя отделяется от аффилиации только по первой
запятой. Значения `-`, `—`, `нет` и `Нет` означают отсутствие соавторов.

Если элемент соавторов нельзя разобрать однозначно, программа не угадывает и
не исправляет его: исходный ответ остаётся в `source.coauthor_answer`, а в
`normalization_issues` и отчёте появляется диагностика. Очевидные ФИО
`И.О. Фамилия` приводятся к `Фамилия И.О.`, полные ФИО сокращаются до инициалов.
Орфография, грамматика и научное содержание не исправляются.
Заголовок, целиком набранный прописными буквами, отмечается
предупреждением в `build/validation.md`.

Тип заявки загружается через `expand=submission_type` и сохраняется в YAML.
Для основных докладчиков из `speakers` также сохраняется поле `email`, если
токен Pretalx даёт доступ к адресу. Для текстовых соавторов адреса недоступны.
Для пленарного доклада применяется узкое исключение: если указан ровно один
докладчик без biography, а ответ на вопрос о соавторах содержит одну строку
организации без запятых и `;`, эта строка используется как аффилиация
докладчика. Исходный ответ всё равно сохраняется в `source.coauthor_answer`.

Порядок секций задаётся `program.sections`, соответствие Pretalx —
`pretalx_section_mapping`. Порядок заявок внутри секции сохраняется из выгрузки.

Для секции `Научно-практические мероприятия` спикер не обязателен; отсутствие
спикера в остальных секциях остаётся ошибкой.

## Редакторская правка

После `normalize` откройте `build/validation.md`, найдите заявку по коду в
`data/proceedings.yaml` и исправьте её нормализованные поля. Для неразобранных
соавторов вручную добавьте элементы в `authors`, а соответствующее сообщение
удалите из `normalization_issues`; `source.coauthor_answer` оставьте без
изменений как provenance. Затем запускайте только:

```bash
uv run esoil-proceedings validate
```

Повторный `normalize` или `all` пересоздаст YAML из raw-файла и затрёт ручные
редакторские изменения. После успешной проверки запустите
`uv run esoil-proceedings build`.

## Семантическая нормализация (схема 2)

Этапы: извлечение полей → rich text → разбор авторов → канонизация организаций →
дедупликация авторов и организаций → назначение ID → keywords → QA → YAML.
Старый YAML схемы 1 необходимо заново получить командой `normalize`.

```yaml
authors:
  - name: Иванов И.И.
    affiliations: [1, 2]
    role: speaker
affiliations:
  1: МГУ им. М.В. Ломоносова
  2: Институт географии РАН
abstract:
  format: richtext
  blocks:
    - type: paragraph
      children:
        - {type: text, text: 'CO'}
        - type: subscript
          children: [{type: text, text: '2'}]
```

Организации сопоставляются только с явным registry
`normalization.affiliation_aliases` в конфиге. Unicode, пробелы и варианты кавычек
нормализуются до сравнения; fuzzy matching отсутствует. Подразделения и адреса
сохраняются. Несколько организаций разделяются по `+`, `;` или переносу строки вне
кавычек и скобок. Запятая разделяет организации только перед целиком известным
alias. При единственной уникальной организации числовые индексы не выводятся.
Повторный автор объединяется по точному нормализованному ФИО с объединением его
аффилиаций и сохранением роли докладчика/email; неоднозначные имена не угадываются.

CommonMark/HTML преобразуются в семантическое дерево до YAML. Поддерживаются
`*italic*`, `_italic_`, `**bold**`, `<em>`, `<i>`, `<strong>`, `<b>`, `<sup>`,
`<sub>`, вложенные inline-узлы и `<br>`. `<p>` и пустая строка задают абзацы,
обычный перенос строки внутри текста — пробел. Пробелы на границах inline-узлов
сохраняются; дополнительные пробелы между ними не вставляются.
Явная научная разметка `10^7`, `CO_2`, `10^{−8}` тоже сохраняется семантически;
из `107` и `CO2` индексы не выводятся. Нумерованные Markdown-списки сохраняют
исходные номера как текст, чтобы парсер не перенумеровал библиографию.

Keywords очищаются от пустых элементов, повторных пробелов, пробелов перед
пунктуацией и завершающих `.`/`;`. Начальная заглавная буква меняется только у
обычных слов из явного `normalization.keyword_common_words`; остальные слова,
аббревиатуры, названия, таксоны и формулы сохраняются.

Диагностики включают `suspicious_author_affiliation_leak`,
`noncanonical_person_name`, `duplicate_author`, `placeholder_email`,
`missing_abstract`, `suspicious_keyword`, `unparsed_coauthor`,
`duplicate_affiliation`, `invalid_affiliation_reference`, а также осторожные
проверки `references_present_but_no_intext_citations` и `mixed_citation_style`.
Научный текст и ссылки не редактируются.
Неоднозначный фрагмент соавтора остаётся в provenance и QA; если в организации
явно обнаружен другой автор, это структурная ошибка. Пропуски и одиночные
сомнительные значения остаются предупреждениями.

```bash
uv run python -m unittest discover -s tests -v
uv run ruff check src tests
uv run ruff format --check src tests
uv run esoil-proceedings all
uv run esoil-proceedings build
uv run esoil-proceedings render-preview
```
